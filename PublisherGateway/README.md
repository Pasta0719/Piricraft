# PiriCraft Publisher Gateway — Deployment gate

**State:** Source and CI are present. No live hosted gateway has been provisioned. Do NOT distribute the client executable until the gateway is live, configured, and has passed the real publishing acceptance test.

## Goal

A trusted collaborator receives exactly one private Windows EXE, selects **existing official MOD update** or **new MOD**, selects a JAR and clicks **更新する**. The collaborator does not need any GitHub account, CLI, login, token entry, Java, .NET SDK or approval from the repo owner.

## Components

- `PublisherGateway/app.py`: HTTPS API receiving signed-off, capability-authorized Fabric JARs, ZIP safety checks, official manifest verification, immutable SHA-256 verification, rate limits, GitHub draft staging, workflow dispatch, and job polling
- `PublisherGateway/WindowsClient/`: source-only WinForms app (not published)
- `.github/workflows/publish-mod-from-app.yml`: existing fail-closed Windows bundling, Check JAR update, boot validation, official release creation and update-manifest.json publication
- `.github/workflows/build-secure-publisher.yml`: gated, manually dispatched owner-only **draft** build. Authenticates to the deployed backend via GitHub Actions OIDC, injects the capability at packaging time, builds, checks UI and stores only in a **draft release**, never public
- `render.yaml`: one Render Free Python instance, GitHub token and public URL set server-side

## Security boundary

The EXE contains a revocable capability that the gateway recognizes, **not** the GitHub publishing token. GitHub credentials are held only on the gateway; the gateway endpoint can only stage MOD files and launch the narrowly scoped workflow.

This is a **bearer-capability model**. Anyone obtaining and reverse-engineering a copy of the EXE can recover its capability. A distributed EXE cannot cryptographically prove its recipient's identity without some external enrollment/authentication. Therefore distribute the EXE **privately only to trusted developers**. Never publish the EXE on the public GitHub release page. If compromised, rotate `PIRICRAFT_GATEWAY_CAPABILITY`, revoke the old binary and build a new private one.

### Credentials and deployment blockers

These are administrative server-side prerequisites, not required of collaborators:

- Render account/service connected and deployment authorized
- Render environment: `PIRICRAFT_GITHUB_TOKEN` = GitHub credential restricted to `Pasta0719/Piricraft` with Contents and Actions write; **never** embedded in the EXE
- Render environment: `PIRICRAFT_PUBLIC_URL` = the gateway's verified HTTPS URL
- Render environment: `PIRICRAFT_GATEWAY_CAPABILITY` generated by Render Blueprint
- Only after a real `GET /healthz` shows `active: true`, use `.github/workflows/build-secure-publisher.yml` with the HTTPS backend URL to privately package the EXE

The Render deployment defaults to its **Free** plan (no paid service automatically purchased). Free instances sleep after periods of inactivity and may take additional time to start. Do not upgrade to a paid plan without the owner's approval.

## Verification gates

1. `test-publisher-gateway.yml`: Python authentication, malicious-archive rejection, remote-list validation, staging flow and invalid OIDC rejection
2. `test-gateway-windows-client.yml`: Windows compile, private-config checks, visible UI controls; produces no publicly downloadable EXE
3. `test-publisher-gateway-live.yml`: real GitHub release staging and workflow dispatch with dry-run set to TRUE, Windows builder result checked and staging draft removed, while official `update-manifest.json` remains unchanged
4. **After actual hosted deployment:** HTTPS health, anonymous access denied, correct capability allowed, JAR upload successful, new EXE and Check JAR release published, update manifest reflects the new version, and auto-update actually downloads and starts the correct version

Until gate 4 is satisfied the application is not complete. Do not provide an EXE download link prematurely.
